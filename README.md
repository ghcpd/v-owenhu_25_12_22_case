# Security audit & hardening — `input.py`

## Overview ✅
This workspace contains:

- `input.py` — **hardened** application (fixed vulnerabilities)
- `input_backup.py` — original file (backup of the insecure version)
- `report.json` — structured vulnerability report and fix explanations
- `tests/` — test runner used to detect the original issues and verify fixes
- `auto_test.py` — automatic test executor (runs platform-appropriate test script)
- `run_test.sh` / `run_test.bat` — per-platform test runners
- `requirements.txt`, `Dockerfile`, `setup.sh` — environment replication and setup
- `logs/test_run.log` — test run logs (generated by `auto_test.py`)

---

## How it was fixed (summary)
- Removed hardcoded secrets; moved to environment variables
- Fixed SQL injection by using parameterized queries and input validation
- Replaced MD5 token generation with HMAC-SHA256
- Prevented SSRF and sensitive-token leakage; added request timeouts
- Replaced shell-based export with `zipfile` and sanitized filenames
- Restricted config file reads to `configs/` directory
- Disabled Flask debug mode by default and added API-key protection for sensitive endpoints
- Added structured logging

## Setup (Linux / macOS / Windows WSL)
1. Create a Python 3.11+ environment and install dependencies:
   - Linux/macOS: `./setup.sh`
   - Windows (PowerShell/CMD): `python -m venv .venv && .\.venv\Scripts\activate && pip install -r requirements.txt`
2. Set required environment variables for production use (optional for local dev):
   - `PAYMENT_TOKEN`, `MAIL_SERVER_KEY`, `SECRET_KEY`, `API_KEY` (defaults exist for local dev)
3. Start the app: `python input.py`

---

## Running tests
- Linux/macOS: `./run_test.sh <module-path>`
- Windows: `run_test.bat <module-path>`

Examples:
- `./run_test.sh input_backup.py` (expected to FAIL — demonstrates vulnerabilities)
- `./run_test.sh input.py` (expected to PASS — shows fixes applied)

### Automatic test (single command)
- `python auto_test.py` — auto-detects platform, runs tests for `input_backup.py` and `input.py` in sequence, and writes logs to `logs/test_run.log`.

Log format includes timestamps and a final `TEST PASSED` or `TEST FAILED` line.

---

## Interpreting results
- `TEST PASSED` (final) — `input.py` passed the security checks and `input_backup.py` still exhibits the original vulnerabilities (expected)
- `TEST FAILED` (final) — either the fixes did not pass tests or the backup no longer shows expected vulnerabilities
